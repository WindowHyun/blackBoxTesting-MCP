# 케이스 스터디 — saucedemo.com

> **상태: 시나리오 설계 완료 · 라이브 실행 대기**
> 설계·검증 세션의 네트워크 정책이 `www.saucedemo.com:443` CONNECT를 403으로 거부해
> (`pypi.org`·`github.com`만 허용) 라이브 실행을 하지 못했다. 아래 "예측"은 실행 **전에**
> 기록한 것이고, "결과"는 비어 있다. 실행 후 채우면 예측 대비 적중률이 그대로 남는다.
> 실행 명령은 [`examples/saucedemo/README.md`](../examples/saucedemo/README.md).

## 왜 이 사이트인가

[saucedemo.com](https://www.saucedemo.com/)은 Sauce Labs가 테스트 자동화 연습용으로
공개한 데모 상점이다. 선택 이유는 하나다: **정답을 알고 채점할 수 있다.** 계정별로
결함이 의도적으로 심겨 있으므로, "도구가 결함을 찾았다"가 아니라 "도구가 *알려진* 결함
중 몇 개를 찾았고 몇 개를 놓쳤는가"를 말할 수 있다. 놓친 것까지 세는 것이 요점이다.

## 테스트 설계

요구사항 ID(`REQ-*`)를 스텝의 `tag`에 달아 리포트에서 역추적되게 했다. 우선순위
(`priority`)는 결제 흐름에 `high`를 몰아, 실패가 여러 개일 때 무엇부터 볼지가 리포트에서
바로 보이도록 했다.

| 시나리오 | 계정 | 통과 기대 |
|---|---|---|
| `happy-path` | `standard_user` | 전부 통과 (기준선) |
| `login-negative` | 빈 입력 / 오답 / `locked_out_user` | 전부 통과 (올바른 에러를 단언) |
| `problem-user` | `problem_user` | **일부 실패해야 정상** |
| `performance-glitch` | `performance_glitch_user` | 통과하되 느림 |

핵심은 `problem-user`가 `happy-path`와 **동일한 단언**을 쓴다는 점이다. 시나리오를 바꾸지
않고 계정만 바꿔 두 리포트를 대조하면, 차이가 곧 결함이다. 결함마다 별도 시나리오를 쓰면
"결함을 이미 알고 그것만 확인한" 셈이 되어 탐지력을 증명하지 못한다.

## 예측 (실행 전 기록)

`problem_user`에서 이 도구가 잡을 것으로 예상하는 지점과, **잡지 못할 것으로 예상하는**
지점을 미리 적는다.

| # | 예상 결함 | 탐지 가능? | 근거 |
|---|---|---|---|
| P-1 | 상품 이미지가 전부 동일한 엉뚱한 이미지 | ❌ **못 잡음** | 이미지 내용 비교(시각 회귀)는 미구현(ROADMAP P6). `snapshot(mode="dom")` 스텝을 넣어 `src` 값이 리포트에 남게 했으니 **사람이** 리포트에서 눈치챌 수는 있다. 자동 탐지는 아니다. |
| P-2 | 체크아웃 성(last name) 입력 불가 | ✅ 잡음 | `#last-name` 입력 후 `#continue` → `checkout-step-two.html` URL 단언이 실패한다. |
| P-3 | 정렬 드롭다운 오동작 | ⚠️ 부분 | `select` 액션 자체의 성공/실패는 잡지만, **정렬 결과의 순서**는 단언하지 않는다. 순서 검증용 어서션 종류가 없다. |
| P-4 | 일부 상품 add-to-cart 버튼 오동작 | ✅ 잡음 | `.shopping_cart_badge` 가시성 / `.cart_item` 개수 단언에 걸린다. |
| P-5 | 미처리 JS 예외 | ✅ 잡음 | 이번에 추가한 `pageerror` 수집(`source="pageerror"`). 이 항목이 이번 개선의 직접적인 시험대다. |
| P-6 | `performance_glitch_user` 지연 | ⚠️ 관찰만 | `duration_ms`로 보이지만 **성능 임계값 단언이 없다**. 느려도 통과로 집계된다. |

예측이 맞다면 6건 중 **완전 탐지 3건 · 부분 2건 · 미탐지 1건**이다. 이 비율 자체가
도구의 정직한 스펙이며, 미탐지 항목은 그대로 백로그가 된다.

## 이미 확정된 한계 (실행 전에도 말할 수 있는 것)

실행 결과와 무관하게, 이 설계 과정에서 드러난 도구의 공백:

1. **시각 회귀 없음** — P-1을 자동으로 못 잡는다. 이미지가 틀린 것은 UI 결함 중 가장
   흔한 축인데 현재 범위 밖이다(ROADMAP P6).
2. **순서/정렬 단언 없음** — `count`는 있어도 "N번째 항목이 X인가"가 없다. P-3의 원인.
3. **성능 임계값 단언 없음** — `duration_ms`는 기록되지만 "3초 넘으면 실패" 같은 단언을
   쓸 수 없다. P-6의 원인.
4. **`wait` 스텝의 `timeout_ms` 누락** — 이 시나리오를 쓰다가 발견해 고쳤다. 러너가
   필드를 버려 모든 대기가 기본 10초로 묶여 있었다. 느린 계정 테스트가 아니었으면
   드러나지 않았을 버그다.

4번은 이 케이스 스터디가 실행 전에 이미 값을 했다는 뜻이다 — 실제 대상을 겨냥해
시나리오를 쓰는 행위 자체가 픽스처로는 안 나오는 결함을 드러낸다.
